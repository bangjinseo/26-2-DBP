# 정책 결정 검토

## 1. 종료된 사업의 PENDING 지출

### 현재 구현

- `PBL_WORKFLOW.SUBMIT_EXPENSE`는 `BUDGET_PROJECT.status='ACTIVE'`인 사업만 신규 지출을 등록하도록 검사함
- `PBL_WORKFLOW.PROCESS_EXPENSE`는 `PROJECT_BUDGET.status='CONFIRMED'`와 지출 한도만 검사하고 상위 `BUDGET_PROJECT.status`는 검사하지 않음
- 롤백 테스트에서 사업을 `CLOSED`로 바꾼 뒤 기존 PENDING 지출을 승인하면 `APPROVED`로 변경됨을 확인함
- 따라서 현재 구현은 종료 사업의 신규 지출은 차단하지만 기존 PENDING 지출 승인은 허용함

### 정책 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 종료 후 승인 허용 | 종료 직전 접수된 지출을 별도 재개 절차 없이 처리 가능함 | 사업 종료 이후 승인 이력이 생기며 종료 시점의 의미와 집계 기준이 불명확해짐 |
| 종료 후 승인 차단 | 종료 시점 이후 신규 재정 확정을 막아 데이터 일관성과 감사 추적이 명확해짐 | 정당한 미결 지출도 사업 재개 또는 별도 정리 절차가 필요함 |

### 추천안

- 종료된 사업에서는 신규 지출 등록과 기존 PENDING 지출 승인을 모두 차단함
- 종료된 사업의 기존 PENDING 지출은 반려 또는 취소만 허용함
- 반드시 승인해야 하는 지출은 사업을 명시적으로 재개한 뒤 승인함
- 사업 재개와 재종료는 처리자·처리일시·사유·변경 전후 상태를 `CHANGE_LOG`에 기록함

### 팀 결정 후 수정 계획

- `BUDGET_PROJECT.status`의 기존 `ACTIVE`, `CLOSED` 값은 유지 가능함
- 사업 상태 변경을 직접 DML하지 않고 `CLOSE_PROJECT`, `REOPEN_PROJECT` 프로시저로 처리하도록 보완함
- `PROCESS_EXPENSE`가 지출·사업예산·사업 행을 잠그고 승인 시 사업 상태 `ACTIVE`를 검사하도록 보완함
- `REJECTED`, `CANCELLED` 처리는 종료 사업에서도 허용하되 처리이력과 `CHANGE_LOG`를 함께 기록함
- 사업 상태 이력이 별도로 필요하면 `PROJECT_STATUS_HISTORY`를 추가하고, 간소화할 경우 `CHANGE_LOG`만 사용함
- 종료 사업 신규 등록 차단, 기존 PENDING 승인 차단, 반려·취소 허용, 재개 후 승인 허용, 로그 실패 전체 롤백 테스트를 추가함
- 기존 PENDING 지출은 일괄 승인하지 않고 담당자가 반려·취소하거나 예외 사유를 남기고 사업 재개 후 개별 승인함

## 2. 기능권한 적용 방식

### 현재 구현

| 업무 | 현재 권한 검사 방식 |
|---|---|
| 학생 본인정보·TOPCIT 조회 | `USER_ACCOUNT.user_type` 직접 검사와 학생 소유권 검사를 함께 수행함 |
| 학생 인적사항 수정 요청 | 학생 소유권과 `user_type='STUDENT'`를 직접 검사함 |
| 학생 수정 요청 처리·학적 변경 | `ADMIN`, `MASTER` 역할명을 직접 검사함 |
| TOPCIT 회차·점수 등록·수정 | `ADMIN`, `MASTER` 역할명을 직접 검사함 |
| 마일리지 신청 | 학생 소유권과 `user_type='STUDENT'`를 직접 검사함 |
| 마일리지 승인·반려·회수 | `MASTER` 역할명을 직접 검사함 |
| 마일리지 대기 취소 | 본인 또는 `MASTER` 역할을 직접 검사함 |
| 지출 등록 | `ADMIN`, `MASTER` 역할명을 직접 검사함 |
| 지출 처리·예산 변경 | `MASTER` 역할명을 직접 검사함 |

- `ROLE`, `PERMISSION`, `ROLE_PERMISSION` 테이블과 초기 매핑 데이터는 존재함
- 업무 패키지에서 기능권한 테이블을 조회하는 `HAS_PERMISSION`, `REQUIRE_PERMISSION` 함수는 없음
- 현재 기능권한 데이터는 설계와 기준정보 역할만 하며 실제 실행 권한 판정에는 사용되지 않음

### 필요한 기능권한 코드

- 기존 코드: `STUDENT_SELF_READ`, `STUDENT_CHANGE_REQUEST`, `STUDENT_MANAGE`, `TOPCIT_SELF_READ`, `TOPCIT_MANAGE`, `AUDIT_READ`, `ROLE_MANAGE`
- 추가 검토 코드: `MILEAGE_SELF_SUBMIT`, `MILEAGE_SELF_CANCEL`, `MILEAGE_MANAGE`, `EXPENSE_SUBMIT`, `EXPENSE_MANAGE`, `BUDGET_MANAGE`, `PROJECT_MANAGE`
- 조회 권한을 더 세분화할 경우 `MILEAGE_READ`, `EXPENSE_READ`, `BUDGET_READ`를 별도로 추가함

### 추천 구조와 매핑

- 역할은 학생·일반관리자·마스터관리자의 기본 분류로 유지함
- 실제 업무 수행 가능 여부는 `ROLE_PERMISSION`과 `PERMISSION.function_code`로 판정함
- 공통 `AUTHORIZATION` 패키지에 `HAS_PERMISSION`과 `REQUIRE_PERMISSION`을 구현함
- 학생 본인 조회·신청·취소는 기능권한 검사 후 학생과 계정의 소유권도 추가 검사함
- 학생 역할에는 본인 조회·수정요청·TOPCIT 조회·마일리지 본인 신청·취소 권한을 매핑함
- 일반관리자 역할에는 학생·TOPCIT 관리, 로그 조회, 지출 등록 권한을 매핑함
- 마스터관리자 역할에는 전체 기능권한을 매핑함
- 권한 코드 또는 역할 매핑이 누락되면 허용하지 않는 방식으로 처리하고 `-20001` 계열 오류를 반환함

### 장점과 주의사항

- 역할명을 패키지마다 직접 비교하지 않아 권한 변경 시 PL/SQL 재배포를 줄일 수 있음
- 같은 역할 안에서도 기능별 최소 권한을 부여할 수 있어 확장성이 높아짐
- 권한 데이터 변경이 즉시 업무 허용 범위에 반영되므로 변경 권한과 검토 절차가 필요함
- 권한 기준정보 누락 시 정상 관리자도 업무를 처리하지 못할 수 있으므로 배포 전 필수 권한 매핑 검증이 필요함
- 권한 변경 이력은 `CHANGE_LOG` 또는 별도 보안감사 로그에 기록해야 함
- 같은 스키마의 직접 테이블 DML 권한이 남아 있으면 패키지 권한 검사를 우회할 수 있으므로 운영 계정에는 패키지 실행 권한만 부여하는 방안을 검토함

### 팀 결정 후 수정 계획

- `PBL_WORKFLOW.REQUIRE_ROLE`과 `STUDENT_TOPCIT_WORKFLOW.REQUIRE_ADMIN`을 공통 `REQUIRE_PERMISSION` 호출로 교체함
- `REQUEST_STUDENT_CHANGE`, `SUBMIT_MILEAGE`, 조회 프로시저의 역할명 비교를 기능권한과 소유권 검사 조합으로 교체함
- 모든 기능권한 코드를 시드에 추가하고 역할별 매핑 누락 검사를 추가함
- 허용·거부, 비활성 사용자, 권한 코드 누락, 매핑 제거 후 즉시 거부, 본인 권한은 있으나 타인 데이터 접근 시 거부하는 테스트를 추가함
- 전체 전환 전까지 현재 역할 직접 검사 코드를 유지하며 일부 업무만 먼저 전환하지 않음
